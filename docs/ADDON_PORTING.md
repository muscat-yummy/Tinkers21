# Addon migration to Tinkers21 / NeoForge 1.21.1

This is a source migration guide, not binary compatibility with Forge 1.20.1 addons. Rebuild against Java 21, Minecraft 1.21.1, NeoForge 21.1.251 and both this branch's TiC and Mantle artifacts. Do not package the in-repository Mantle classes into your addon. Preserve original namespaces and attribution. A public release also needs the presentation/policy review already recorded in PORTING.md.

## Audited source and scope

Reference: [TiCEX 1.20.1, commit 94588a39](https://github.com/mofumofumoffy/ticex/tree/94588a39bce40cb7f5a7992eb071753e0f3fa397). Inspection on 2026-10-11 covered its Java import inventory and representative registration, modifier, recipe, persistence, networking, capability and Mixin call sites. There are 297 distinct imported TiC/Mantle symbols and 1,055 import occurrences. Every imported name has a corresponding enclosing source-owner path in this repository. This checks preserved packages only: nested/member existence, signatures, access, linkage, third-party APIs and runtime behavior do not follow from this count. No TiCEX jar was loaded or built in this audit.

The phase's practical boundary is documented API differences and independent addon acceptance. A full TiCEX port, all its optional integrations, external mods such as Diet and arbitrary legacy worlds require separate projects/validation.

## Contracts and concrete migration points

| Area | Reference addon call sites | Retained contract / required change |
| --- | --- | --- |
| Mod initialization and registration | `modules/general/TicEXRegistry.java`, `TicEX.java` | Use the addon constructor's injected NeoForge `IEventBus`. Existing `ModifierDeferredRegister.create(modId)`, `register`, `registerDynamic`, `StaticModifier` and `DynamicModifier` remain. Attach the register to the addon bus; do not use TiC's bus. Resolve static modifiers after registration and dynamic modifiers after reload. Forge item/fluid registers and `RegistryObject` need native equivalents. |
| Materials and tool definitions | `item/modifiable/ModifiableGunItem.java`, `lib/recipe/EmbossmentBuildingRecipe.java` | `MaterialId`, `MaterialVariantId`, `MaterialRegistry`, `IModifiable`, `ToolDefinition`, `MaterialNBT` and `ToolStack.createTool` remain. Material lookup occurs after actual reload. Data lives under `data/<addon>/tinkering/materials/{definition,stats,traits}`. Client render data uses `assets/<addon>/tinkering/materials`; retain material IDs across both sides. |
| Static and dynamic modifier hooks | `modifier/ModifierOverload.java`, `lib/hook/TicEXModifierHooks.java` | `Modifier`, `NoLevelsModifier`, `ModifierEntry`, `ModifierHooks`, `ModuleHook`, `ModuleHookMap.Builder` and hook-based composition remain. The retained static `registerHooks` override is deprecated upstream but supported. Prefer dynamic `ModifierModule`/record loaders for data-driven logic. Custom hooks still need registration and a defined dispatcher; creating a hook does not cause TiC to call it automatically. |
| Modifier-owned storage | `modifier/ModifierHiddenProud.java`, `ModifierKoshirae.java`, `ModifierReactive.java`, `ModifierMekanic.java` | Replace `ItemStack.getOrCreateTag()` / `getTag()` with typed native components or `ToolStack.from(stack).getPersistentData()` writes under addon-owned `ResourceLocation` keys. The tool view writes through to native components. Read getters return snapshots; mutate via `put`, `putInt`, `copyFrom`, etc. Detached NBT from `ToolStack.from(item, definition, tag)` is not an attached ItemStack view. A component read followed by mutation of its copied tag does not update the stack. |
| Vanilla item state / nested stacks | `modifier/ModifierOverload.java`, `lib/recipe/EmbossmentCastingRecipe.java`, `item/projectile/MekanicShotItem.java` | Enchantments, names, attributes, potion contents and durability use native Data Components/holders, not old `Enchantments`, `display` or `Damage` NBT writes. Nested stacks require registry-aware native codecs/save/load and component preservation. Tool storage modules own inventories/fluids separately; keep metadata and content in their respective APIs. Legacy `embossed`, `bladeState` and `shooterItem` payload conversion is the addon's responsibility, not automatically handled by TiC's bounded core migration. |
| Recipes and datagen | `lib/recipe/EmbossmentBuildingRecipe.java`, `EmbossmentCastingRecipe.java`, `datagen/general/recipes/apotheosis/ApotheosisEnchantingRecipeBuilder.java` | Mantle loadable/type-aware serializers remain, backed by native map/stream codecs. Recipes require the native `RecipeInput` boundary and registry-aware `assemble`/serialization. `RecipeHolder` owns recipe IDs. Use `HolderLookup.Provider.createSerializationContext` when encoding registered holders. Use native singular `recipe`, `advancement`, `loot_table`, `structure` directories and component JSON. Do not reconstruct an ownerless registry context or emit old output `nbt` blindly. |
| Item capabilities | `item/modifiable/ModifiableGunItem.java`, `lib/utils/TicEXCuriosUtils.java` | `ToolCapabilityProvider.register` still adds constructors; constructors must be stateless and use the supplied live tool view. Replace Forge `Capability`/`LazyOptional` with `ItemCapability<T,Void>`. Register custom dispatch via `ToolCapabilityProvider.registerCapability(event, capability)` in `RegisterCapabilitiesEvent`; query via `stack.getCapability`. Retained providers must refresh after tool component changes. Curios requires its own matching native API; TiC cannot adapt Forge Curios types. |
| Fluid/machine integration | TiCEX's `FluidTransmuter` recipes/menus and embossment casting | Resolve native item/block fluid capabilities and pass actual level, block position/state/entity context. Retain live master lookup and capability invalidation for formed structures. Mantle's ingredient wrappers implement native custom ingredients: use their vanilla wrapper (`toVanilla` / factory result) at `Ingredient` call sites. JSON `nbt` transfer IDs may remain but the underlying payload is native components. |
| Networking and menus | `TicEX.java`, addon network messages and menu registrations | TiCEX creates Forge `SimpleChannel` directly: this must change. Mantle `NetworkWrapper` retains encoder/decoder/handler registration but wraps NeoForge payloads, with Mantle `NetworkDirection` and `NetworkEvent.Context`. Register packets during construction and attach `registerPayloads` to the addon mod bus before the payload event. Use registry-aware buffers for item/holder codecs. Handler mutation uses `enqueueWork`; validate direction/sender. Native menu IDs and actual close packets govern reopening. |
| Rendering and armor | `mixin/MaterialArmorTextureSupplierMixin.java`, `TrimArmorTextureSupplierMixin.java`, `HumanoidArmorLayerMixin.java`, `ItemRendererMixin.java` | Keep material compositing; register native geometry/sprite/reload hooks. The four human armor types are `ModifiableArmorMaterial.ARMOR_TYPES`; vanilla `ArmorItem.Type.values()` additionally includes BODY. Explicitly support BODY when needed rather than indexing it into four-slot arrays. Native armor item extensions and texture suppliers replace old Forge hooks. Every Mixin target descriptor, injection point, field layout and refmap must be audited against the rebuilt native class. |
| Combat/loot events and internal access | `mixin/CriticalAccessor.java`, `modifier/ModifierOmnipotence.java` | Public context/hook APIs are preferred to private-field Mixins/reflection. `ToolAttackContext.criticalModifier` still exists but remains an internal field and its lifecycle is native critical handling. `ModifierOmnipotence` reflects on `committee.nova.mods.avaritia.util.ToolUtils.sweepAttack`, an external Avaritia API, not a TiC API. Audit it against that mod's native artifact independently; do not silently skip failed reflection. Native critical, projectile, damage, enchantment and loot holder/event contracts differ from Forge. |
| Optional external integrations | TiCEX Mekanism, Apotheosis, SlashBlade, Curios, Draconic Evolution, ProjectE, etc. | Conditional mod presence does not establish native API compatibility. Port each integration against its actual 1.21.1 artifact, isolate optional class loading, and test absent/present cases. The port's own Diet reflection adapter remains unverified with an external runtime and must not be advertised as proven compatible. |

## Independent acceptance fixture

`src/portAddonCheck` is an independently compiled test source set with its own `portaddoncheck` mod ID, metadata and constructor-injected bus. It is loaded only when the existing `portGameTests` or `portClientCheck` properties are enabled. It is not included in either production jar or normal runs, and adds no production dependency.

The fixture tests real addon-owned static registration (including rejecting a duplicate without replacing the first supplier), an addon-created custom hook, a native stat hook, dynamic modifier/material/stat/trait resources, tool stat rebuild/removal, registry-aware ItemStack codec round trips, write-through state and copy isolation. An addon-created native item capability is registered and queried through TiC's public provider extension; a retained handler must observe component changes. The graphical gate additionally sends a request and reply over an addon-owned Mantle payload channel, receives the actual server inventory update, verifies the addon material/modifier/state on the client and bakes native material geometry. Existing core regression markers remain required.

No test simulates an installed TiCEX binary. The fixture demonstrates the specified public extension boundary. It does not validate all custom tool item classes, custom recipe implementations, every private Mixin or every external integration.

## Recommended TiCEX port sequence

1. Create a Java 21 / NeoForge 1.21.1 addon workspace against these TiC/Mantle artifacts. Port mod-bus registration and retain the original `ticex` namespace. Start with a single material, modifier and tool definition, then run native server/client checks.
2. Port native components, nested items, recipe inputs/serializers and payload/menu handling before expanding gameplay. Define explicit old addon-data migration separately from fresh-world behavior; test save/reload, copies and multiplayer transactions.
3. Register custom capability dispatch and custom module loaders/hooks. Verify a live native capability after component mutation and data reload, and verify custom hook dispatch rather than only loader registration.
4. Port client assets and rendering with actual native resources. Audit each Mixin/reflection dependency individually; replace private access with public APIs where practical.
5. Enable external integrations one at a time against their actual native artifacts, testing absent and present configurations. Only then claim compatibility for that exact addon/mod/version matrix.
